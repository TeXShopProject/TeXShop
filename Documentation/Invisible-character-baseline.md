# 不可視文字のベースライン修正（2026-10-07）

## 原因

TSLayoutManagerは本文のベースラインを使わず、行上端から4ポイント引いた位置にNSStringのdrawAtPoint:withAttributes:で記号を描いていた。コンテナの描画原点も無視していた。このコードはv.5.20.2と修正前5.58.7で同一。

TeXShopHighSierra.zipの実物は5.20.2、SDKは14.4、Info.plistのLSMinimumSystemVersionは10.13.0だった。5.58.7の同値は14.6。本家5.58取り込みfa188abがこの値を変更した。5.57取り込み1424335時点は10.13.0のままであり、この実験から5.57でも発生するとまでは言えない。

Golden Gateで両実行ファイルのTSLayoutManagerを直接呼ぶ実験を行った。複製バンドルに診断用ライブラリを読み込み、アプリのmain・文書初期化前に描画と終了を実行した。ユーザーの文書、Preferences、Libraryを変更する本体処理は実行していない。

HiraginoSans-W3 24pt、同じ文字列・座標で本文は一致したが、新版の記号だけが2ポイント上に描かれた。旧バイナリを変更せずInfo.plistのLSMinimumSystemVersionだけを14.6にすると、新版と描画ピクセルが完全一致した。10.13.0に戻すと旧版と一致。10.14、11.0、12.0も新版と一致した。Mach-OのSDK指定だけを27.0にしても旧表示のままだった。

したがって同じOSでも最低対応OSの宣言によるNSString描画の互換動作が異なり、従来の固定補正が合わなくなったと切り分けられる。OS内部の具体的な分岐実装は未調査。旧・新nibのテキストビューを本体から独立して読み込んだ比較では、同じフォントでコンテナ原点・ベースライン・行高は一致した。

## 修正

記号もNSLayoutManagerでレイアウトし、そのベースラインを本文のベースラインに合わせる。描画原点・行位置を加算し、文字位置のフォントを使う。同じ記号とフォントのレイアウトは1回の描画中に再利用する。最低対応OS宣言を巻き戻して解決しない。

## 検証

- Tests/run-invisible-baseline.sh: 半角／全角スペース、タブ、改行、フォントとサイズ4条件、混在フォント、行間、字下げ、非ゼロ原点の32ベースラインを検証。
- 同じテストをLSMinimumSystemVersion=10.13.0と14.6のバンドルで実行し、出力のピクセルバッファも完全一致。
- 描画画像を目視確認。社内版と国際版のDebug／Releaseビルド成功。
- 実際のTeXShopの文書ウィンドウを開くGUI操作はこの検証に含めない。
